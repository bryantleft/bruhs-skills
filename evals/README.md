# Evaluations

Each folder in this directory is one test case: a scaffold that builds the
workspace, a realistic prompt, and graders that say what a good run looks like.
The layout is the one [`claude plugin eval`](https://code.claude.com/docs/en/plugin-evals)
reads, and also what skill-creator reads. Every file is plain Markdown, YAML or
bash, so the same cases work with any agent: Claude Code, Codex, Grok CLI, Cursor,
Gemini CLI, or anything else that loads `skills/bruhs/SKILL.md`.

The deterministic script tests live in `tests/` and need no model:
`bash tests/run_script_tests.sh`. That run also builds every case's workspace,
checks the generated mocks, and validates every case, so run it after any change
here.

## Case layout

```
evals/
├── _lib/                         # shared by every scaffold (not a case)
│   ├── helpers.sh                # eval_repo, eval_state, eval_origin, eval_gh, ...
│   ├── gh_pr_fixtures.sh         # PR/review/checks answers for peep and dip
│   ├── gh_world.py               # stateful fake GitHub + CI for yeet and land
│   ├── walk_pr.sh                # gh answers for one PR, built from the real diff (walk)
│   └── recap_dates.sh            # commits at dates relative to today (recap)
└── cook-from-ticket-id/          # case name: what the test checks
    ├── scaffold.sh               # builds the workspace the prompt expects
    ├── prompt.md                 # run settings, then the user's message verbatim
    ├── case.yaml                 # name, preconditions, expected outcome, scaffold_script
    ├── graders/
    │   ├── 01-step-0-confirms-bruhs-state-block-in.md
    │   └── ...                   # one claim per file; the last one is the failure modes
    └── mocks/linear-perdix/      # generated: the Linear server the case's state names
```

- **`scaffold.sh`** runs in the empty workspace before the agent starts. It
  sources `_lib/helpers.sh` and builds exactly the preconditions in `case.yaml`:
  a git repo with real history, `bruhs:state` and `bruhs:rules` blocks written by
  the skill's own scripts, the code under test with the planted problem and a
  decoy, a local bare `origin`, and `gh` answers. Read the header of `helpers.sh`
  for every helper.
- **`prompt.md`**: the frontmatter holds the run limits and `tags` (the command
  under test). The body is what a user would type. An unknown frontmatter key
  makes the case fail to load, so free text goes in `case.yaml`.
- **`case.yaml`**: `schema_version: "1.1"` (quoted), `name` (same as the folder),
  `description` (command, preconditions), `expected_outcome`, and
  `context.scaffold_script`.
- **`graders/NN-*.md`**: mostly `type: llm` rubrics in prose. Where a claim lives
  in the middle of a long run, the grader reads a file instead of the transcript
  (`focus: { source: file, path: .git/local/ledger.md }`, written by `gh_world.py`)
  or the mocked MCP calls (`focus: mock_calls`).
- **`mocks/<server>/`**: Linear mocks are generated by `tests/sync_eval_mocks.py`
  from `tests/fixtures/linear-mock/`, one copy per Linear server a case's
  scaffold names in `"mcpServer"`. Don't edit them; edit the template or the
  ticket fixtures in `tests/fixtures/linear-mock/fixtures/<ID>.json`, then rerun
  the sync. Other servers (tldraw for doodle, sentry for one peep case) are
  hand-written per case.

## What a run is like

These are properties of `claude plugin eval` runs, checked with probe runs, and
the fixtures are built around them:

- **Empty, isolated workspace.** A fresh temporary HOME, no personal settings,
  MCP servers or skills, and no `CLAUDE.md` auto-loading. bruhs reads
  `CLAUDE.md` itself, so the scaffolded blocks still drive it.
- **No network.** The stub `gh` (`.git/local/bin/gh`) answers from the case's
  fixtures and logs every call to `.git/local/gh-calls.log`. An unknown call
  fails with `HTTP 404: Not Found`. The offline `npm` runs `package.json`
  scripts and fails installs. `eval_node_project` writes `typecheck`, `lint` and
  `test` scripts that really run on Node built-ins.
- **No real home directory.** The sandbox can't read the user's home, so
  toolchains installed there (pyenv, anaconda, nvm) can't start. The run's PATH
  puts `.git/local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` and
  `/bin` first.
- **`.git/config` is read-only.** `git push -u` pushes but prints an upstream
  error. `eval_origin` sets upstreams ahead of time, and graders ignore that
  message.
- **No questions.** `AskUserQuestion` doesn't exist in a headless run: the agent
  asks in plain text and the run ends there. A case either tests that question
  (graders stop at it) or pre-answers it in the prompt the way a user would ("go
  with your recommendation, I'm away").
- **The judge sees part of the transcript.** An `llm` grader with `focus: trace`
  sees the first 12 and last 12 messages. That's why mid-run claims are graded
  from files or mock calls.

Requirements on the machine running the suite: git, python3, node 22.6+ and jq
outside the user's home directory (Homebrew or system packages), plus Claude
Code v2.1.269+ for `claude plugin eval`.

### Keeping graders provider-neutral

Grade what the agent did, not which harness tool it used. Graders that name a
Claude Code tool (`AskUserQuestion`, `ToolSearch`, `Task`, `mcp__*` names) end
with a note telling the judge that the equivalent mechanism on another harness
counts. `skills/bruhs/references/harness-tools.md` is the full mapping. Add the
same note to any new grader that names a harness tool, or better, describe the
behavior instead ("asks the user to pick an approach").

## Running the cases

### Claude Code (`claude plugin eval`)

From the repo root:

```bash
# one case, one run, no baseline: the cheapest end-to-end check
claude plugin eval . --case cook-from-ticket-id --scaffold \
  --allow-tools Bash Write Edit --runs 1 --ablation none

# every case for one command, with the no-plugin baseline
claude plugin eval . --tag peep --scaffold --allow-tools Bash Write Edit
```

`--scaffold` is required: without it no workspace is built. These are real,
billed model runs. The full suite is 71 cases × 3 runs × 2 arms, roughly 430
agent runs plus 3 judge calls per `llm` grader per run, so filter with `--case`
or `--tag`, and try `--model haiku` while iterating on graders. Results go to
`evals/results/` (gitignored).

### Any other agent

1. Make an empty directory and run the case's scaffold in it:
   `mkdir /tmp/run && cd /tmp/run && bash <repo>/evals/<case>/scaffold.sh`.
   Outside `claude plugin eval` it never touches your shell rc files. It prints
   the `export PATH=...` line that puts the stub `gh` and offline `npm` first;
   run that line in the shell you start the agent from.
2. If the case has `mocks/<server>/`, serve those tools to your agent under that
   server name. Each `<tool>.md` body is the tool's answer, and
   `fixtures/<ID>.json` holds the ticket bodies. Or answer the calls yourself
   from those files. `_tools.json` has the input schemas.
3. Start the agent in that directory with bruhs installed and send the body of
   `prompt.md` as the user message.
4. Grade the transcript against each file in `graders/`, recording pass/fail
   with evidence. A second model reading the transcript and the grader files
   does this well.

For runners that read the agentskills.io format (a single `evals/evals.json`),
generate one:

```bash
python3 tests/export_evals_json.py -o /tmp/bruhs-evals.json
```

Each case becomes one entry with `prompt`, `expected_output`, `assertions` (one
per grader), and two extra fields: `context` (the preconditions) and `setup`
(the scaffold to run first). Copy the file to wherever your runner expects it,
but not to `evals/evals.json` in this repo: skill-creator would then run every
case twice.

## Adding a case

1. Create `evals/<command>-<what-it-tests>/`: lowercase letters, digits and
   hyphens, starting with a letter, and not `results`, `mocks`, `files`,
   `node_modules`, `true`, `false` or `null`.
2. Copy `scaffold.sh`, `prompt.md`, `case.yaml` and a grader from a case close to
   yours. Build only what the graders need, and plant both the problem and a
   decoy, so a run without the skill's guidance plausibly gets it wrong.
3. Write one grader per observable claim, plus one for the failure modes. Make
   every grader reachable in one headless run.
4. New Linear tickets go in `tests/fixtures/linear-mock/fixtures/`. Then run
   `python3 tests/sync_eval_mocks.py` and `bash tests/run_script_tests.sh`. Both
   are free.

### Cross-cutting flows

These cases span several commands or test the invariants of the marker-block
system:

- `claim-legacy-bruhs-migration`: port `.claude/bruhs.json` to marker blocks
- `claim-migration-redetect`: ignore the legacy file and re-detect from code
- `claim-marker-and-legacy-both-present`: Case A wins when a marker block and the
  legacy file both exist
- `cook-persists-discovered-skills`: newly discovered skills round-trip back into
  `bruhs:state`
- `cook-no-receipt-no-number`: operational limits need evidence, and a missing
  receipt becomes measurement work
- `slop-landmine-tripwire`: delayed failures, false success and unguarded
  assumptions use the shared vocabulary

Run these whenever the migration path, the marker format, or the mirror invariant
(`CLAUDE.md` ≡ `AGENTS.md` inside the blocks) changes.
